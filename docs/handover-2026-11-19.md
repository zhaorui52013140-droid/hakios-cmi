## 3. 上机与停机流程

### 3.1 启动前必须先确认状态

```powershell
D:\hakios-build\pt\platform-tools\adb.exe devices -l
D:\UotanToolbox\Bin\platform-tools\fastboot.exe devices
```

手机可能处于 Android、Xiaomi bootloader、xnuloader、iOS 或断连状态，不要假设。

### 3.2 21:39 基线复跑

```powershell
# Android → Xiaomi fastboot
adb -s <serial> reboot bootloader
# 等约 20 秒，确认 fastboot devices 可见

# 启动 hakios loader
fastboot boot D:\hakios-build\cmi-out\hakios-cmi-boot-tail.img
# 等约 15 秒，fastboot devices 应显示 xnuloader

# 每次完整上机都重新执行，避免根盘选择错误
fastboot oem ramdisk
fastboot stage D:\hakios-build\cmi-out\system-zh7.apfs   # 约 109 秒
fastboot stage D:\hakios-build\cmi-out\payload-bt1.bin
fastboot oem run
fastboot getvar result                                  # 期望 running 0 0
```

启动成功判据之一：

```text
resident image at pa fc000000 size a5818000: it is the root (md0), the payload ramdisk is md1
```

### 3.3 停机与日志

```powershell
fastboot oem stop                  # 有时需要两次
fastboot getvar result             # 等 returned <bytes> 0
fastboot oem log
fastboot get_staged <本地文件名>.log
```

- stop 后通常只能取前 **262,143 B**，这是初始化/启动段分析的关键材料。
- 运行中日志必须在 stop 前抓；本轮 `baseline-2203-live1.log` 只有 16,375 B，是 loader heartbeat 摘要，不是完整内核环。
- 看 `thyme: input init`、modem/Bluetooth 初始化等早期内容，以 stop 后启动段为准。
- 内核仍 `running` 时不要直接 stage/run；先 stop 并确认 `returned`。

### 3.4 回 Android

```powershell
fastboot reboot
```

## 6. 触摸回归：bt1 正常、bt2 异常

### 6.1 当前验收

2026-11-19 使用 **`system-zh7.apfs + payload-bt1.bin`** 原文件上机，`getvar result` 为 `running 0 0`，用户实际触摸后明确回复“恢复”。

同一 `system-zh7.apfs` 下，此前使用 **`payload-bt2.bin`**（21:46 生成，曾被误称为“22:03 基线”）时用户报告无触摸。两包 kernel、总大小、cmdline 相同，只有 ramdisk 不同。

### 6.2 日志能证明什么

bt1 与 bt2 的启动段都能看到 FTS521 完成初始化：

```text
resident image at pa fc000000 size a5818000
UMI FTS: ST FTS521 3639 initialized scan=0x1
UMI FTS: sysinfo err=0 hdr=a5 fw=0123 afe=08/08/08
thyme-touch: reader opened (pid 25/26)
thyme-touch: reader opened (pid 15)
thyme-touch: reads 1
```

bt1 启动窗口内 `UMI FTS` 多次轮询均为 `events=7 errors=0 irq=1 active=0`。这只说明日志窗口内没有新增触点报文，**不能反推用户每次触模都没有中断**。

能下的结论：

- FTS521 控制器在 iOS 下能上电、初始化、被 touch reader 打开；
- bt1 与 bt2 的差异不在 system.apfs，也不在 kernel；
- 当前可触摸基线是 bt1，不是 bt2。

不能下的结论：

- 不能仅凭启动段 `events=7` 断言物理触摸没有产生中断；
- 不能认定 App 固化、GPU/ADSP 地址冲突或 AVRCP/LE job 是已证实根因；
- 不能用 VM 当前 `root.apfs` 冒充 bt1 的 ramdisk。

### 6.3 旧“地址冲突”解释已撤回

`app1_live.log` 中大镜像启动时，zap header 临时页地址会随布局变化（例如 `0x1b246c000`），但真正 zap shader 目标仍为 `0x8681a000`，且日志明确显示：

```text
TRUSTZONE HAS AUTHENTICATED AND STARTED THE ZAP SHADER
THE GPU STAYS ON for the system to draw with
```

因此“镜像变大覆盖固定 GPU/ADSP 固件地址导致触摸丢失”证据不足，后续不要据此改 loader 或裁 modem 固件。

### 6.4 下一步

1. 离线解开 bt1 与 bt2 的 ramdisk，列出全部文件级差集和权限/符号链接变化。
2. 对差集中的候选改动做单变量复测：以 bt1 为底，只加入一项，再上机验收触摸。
3. 若需要抓触摸运行段，先与用户约定开始触摸时刻，再 stop 取启动段；不要把 262 KB 启动窗口当作完整触摸记录。
4. 差集未闭合前，不重编、不固化 App、不做双系统分区。

## 15. bt1 / bt2 ramdisk 差集（2026-11-19 08:26 完成，已归档）

### 15.1 结论：差集只有 5 个文件

`payload-bt1.bin` 与 `payload-bt2.bin` 的内核（`ab0d6e6b…`）、cmdline（`b49a1cde…`，含 `touchscreen=1`）、镜像大小（38,068,224 B = 9294 块）全部相同。ramdisk 全量清点后，**文件级差异只有下面 5 条**：

| # | 路径 | bt1 | bt2 | 变化 |
|---|---|---|---|---|
| 1 | `/etc/motd` | 47 B | 47 B | 仅构建时间戳（21:24 → 21:46） |
| 2 | `/LaunchDaemons/com.apple.backboardd.plist` | 1086 B | 1024 B | **删除了 `EnvironmentVariables{OS_ACTIVITY_DT_MODE=YES}`** |
| 3 | `/LaunchDaemons/com.apple.bluetoothd.plist` | 1270 B | 1302 B | 增加 `OS_ACTIVITY_DT_MODE=YES` |
| 4 | `/LaunchDaemons/com.apple.BTServer.avrcp.plist` | 无 | 365 B | 新增 job（`/usr/sbin/BTAvrcp`） |
| 5 | `/LaunchDaemons/com.apple.BTServer.le.plist` | 无 | 504 B | 新增 job（`/usr/sbin/BTLEServer`） |

除此之外 543 个条目的路径、权限、uid/gid、大小、哈希全部一致；`/lib/libhakios*.dylib`（含触摸上报的 `libhakios.dylib`，73,712 B，`30b084ff00e100ae`）两包完全相同。

### 15.2 差集的成因（可解释）

`mkjobs.py` 只对 `OSLOG` 里点名的 job 设 `OS_ACTIVITY_DT_MODE=YES`。bt1 的 OSLOG 点了 `backboardd`；bt2 换成 `com.apple.bluetoothd com.apple.BTServer.avrcp com.apple.BTServer.le`（即第 4 节文档里那条蓝牙诊断命令）。两个新 job 由 `build.sh` 的 `BLUETOOTH=1` 加入 `IOS_JOBS`。

### 15.3 日志对比的一条重要方法论修正

bt1 与 bt2 的 262 KB 启动段**不能直接比“少了哪些行”**：bt2 把 `DT_MODE` 开在日志极多的蓝牙进程上，窗口被蓝牙日志填满，backboardd 的 `[Backlight]`、`[UISensor]`、`PUIProgressWindow` 等行被挤出窗口。实测 bt1_stop 有 2 条 Backlight / 1 条 PUIProgressWindow，bt2_stop 为 0，但两者的内核时间都覆盖到 178–187 s，**这属于取样偏移，不是功能缺失的证据**。

### 15.4 触摸正常/异常的可用判据（保留备用）

`libhakios.dylib` 注入 backboardd 后从 `/dev/thyme-touch` 取点，每有点会打印 `hakios: input: sample type N finger N at X Y`；另有 `hakios: input: touch detection mode 0xfe/0x1/0` 表示 backboardd 已把扫描模式下发到 digitizer。bt1 运行期日志有样点、bt2 与固化 App 那两次为 0。这条判据**只用于未来验证，不再用于追 bt2**。

### 15.5 VM 构建树与 bt1 的关系（2026-11-19 08:27 核对）

`/home/cmi/hakios/userland/userland/root.apfs`（38,068,224 B，`cc4133fb31b2eec4c07c661d631cbfdb`）与 bt1 的 ramdisk（`6cd562a0…`）逐文件比对，差异只有：

- `/etc/motd` 时间戳不同；
- 多出 `com.apple.BTServer.avrcp.plist`（285 B）与 `com.apple.BTServer.le.plist`（472 B）两个 job，**且不带 `OS_ACTIVITY_DT_MODE`**（与 bt2 的 365/504 B 版本不同）；

即当前 VM 树 ≈ bt1 + 两个 BT job，可作为后续增量修复的起点。**但它的 MD5 不等于 bt1，复现触摸基线仍必须直接用 `payload-bt1.bin` 原文件。**

## 19. A2DP 卡顿的根因：蓝牙 UART 被钉死在 115200（2026-11-19 09:40 定位）

### 19.1 结论

**不是 Wi-Fi 共存，不是调度，是带宽物理不够。** 蓝牙 UART 主机侧与控制器侧**两端都被写死为 115200**，而 115200 8N1 的物理上限是 11.5 KB/s ≈ **92 kbps**；A2DP 的 SBC 立体声需 229～345 kbps（AAC 约 256 kbps）。差 3～4 倍，因此必然是「进度条正常推进、声音持续断续」，与用户实测一致（时有时无、持续不断）。

三重印证：

1. **启动日志**：`UMI BT: loading htbtfw20/htnv20 at 115200 baud (Hastings tag17 byte1)` —— 全流程都在 115200。
2. **代码把控制器端钉死**：`mi10-new/overlays/xnu/files/bsd/sys/hakios.bluetooth.h:85`
   `data[hci + 1] = 0; /* QCA_BAUDRATE_115200 */`
   —— 把 NVM 里 tag 17 的波特率字节强行改写成 0（115200），等于把 Android 出厂的 3.2 Mbaud 降下来。
3. **主机端也钉死**：`umi_bluetooth.c:418` 拒绝任何非 115200 的 termios（`return EINVAL`），`umi_bluetooth.c:510` 把 `c_ispeed/c_ospeed` 都设成 115200。

### 19.2 参考实现怎么做的

根目录 `instantnoodle_bt.c`（OnePlus 8 Pro，A2DP 已验收可用）的做法是：

- 固件下载与 HCI_Reset **仍在 115200**；
- NVM 的 tag 17 byte 1 保持 `0x11`（= 3,200,000 的编码），控制器在 Reset 后自行切到 3.2 Mbaud；
- **Reset 之后**主机再切：`uart_baud(3200000, 64, 375, 1)` —— GPLL0 300 MHz × 64/375 = 51.2 MHz，引擎分频 1，该引擎 16 倍采样 → 3.2 Mbaud。

原注释里的血泪教训（务必照做，不要改顺序）：

> …only then does the host change its rate. Earlier runs skipped that reset and talked at 3.2 Mbaud to a controller still waiting at 115200: … answered a wake-up with a firmware crash report; wrong-rate bytes make it flood.

### 19.3 修复清单（只动 kernel，不动系统镜像）

1. `hakios.bluetooth.h`：`data[hci + 1] = 0` → `0x11`（或直接保留文件原值不改写）。
2. `umi_bluetooth.c`：把 `bt_uart_clock()` 参数化（M/N + 引擎分频）。当前 384/15625（7.3728 MHz）+ 分频 4 = 115200；3.2 Mbaud 用 64/375（51.2 MHz）+ 分频 1，并写 `GENI_SER_M_CLK_CFG`/`S_CLK_CFG` 的 `${SER_CLK_EN | div<<CLK_DIV_SHFT}`（参考 `uart_baud()`）。
3. `bt_qca_firmware()`：`HCI_Reset(0x0c03)` 在 115200 收到完成事件**之后**，再切主机到 3.2 Mbaud，随后用 `0x1001` 在新速率上验证一次。
4. `bt_control_setopt` / `bt_control_termios`：接受并上报 3200000，别再拒绝。
5. 观察点：3.2 Mbaud 下 worker 的 `delay(1000)`（1 ms 轮询）是否够用；若出现 `UMI BT: TX timeout` 需要收紧轮询或依赖硬件流控。

**风险与回滚**：这是 kernel payload 的改动，**系统镜像 `system-zh7-btaudio.apfs` 完全不动**，`payload-bt1.bin` 保留为回滚件。构建需要 Ubuntu VM（`D:/Ubuntu 64 位\Ubuntu 64 位.vmx`）在线——`build-kernel.sh` 走 Linux + XNU 源码，Windows 侧跑不了。

### 20.1 修改内容

| 文件 | 改动 |

### 20.2 时钟换算（关键，别改错）

现有驱动 115200 的实证配置：根时钟 7.3728 MHz（384/15625）、引擎分频 4（`GENI 0x48/0x4c = 0x41`）、16 倍采样 → `7.3728/4/16 = 115200`。

因此 3.2 Mbaud 需要 **51.2 MHz 串行时钟**，两种等价写法（代码里依次尝试）：

1. 根 204.8 MHz（256/375）× 分频 4 —— 只动 M/N，分频沿用现有值；
2. 根 51.2 MHz（64/375）× 分频 1（`0x11`）—— 与 `instantnoodle_bt.c` 完全相同。

两者串行时钟同为 51.2 MHz，所以第一种失败后切第二种不会让控制器失联。

### 20.3 时序（不可颠倒）

固件补丁 → NVM（tag17 byte1 = 0x11）→ 关诊断日志 → **HCI_Reset**（控制器在此切到 3.2 Mbaud）→ 主机切 3.2 Mbaud → 用 `0x1001` 验证 → 继续 `0x1002`/`0x1009`。

### 20.4 自动回退

若两种时钟写法都收不到 `0x1001` 回复，`bt_qca_firmware` 返回 `EAGAIN`，`bt_hci_probe` 会：拉低 GPIO21 重新上电 → 复位 UART 引擎与 H4 状态 → 冷复位 → **以 115200 重跑整段下载**。即使新速率判断错误，蓝牙也不会变砖，只是回到卡顿状态。

### 20.5 产物

`cmi-out/payload-bt1-3m2.bin`（54,174,680 B）。逐项核对：

| 项 | 旧 `payload-bt1.bin` | 新 `payload-bt1-3m2.bin` |
|---|---|---|
| kernel | 16,073,168 / `ab0d6e6b…` | **16,106,032 / `2832ac3c…`** |

### 20.6 上机判据

启动日志里应出现：

- `UMI BT: link at 3.2 Mbaud: root 256/375 cfg 0x41 GENI 0x41/0x41 GCC 0x100/0xff88/0xfe88`

## 21. A2DP 卡顿：3.2 Mbaud 尝试记录与未完线索（2026-11-19 11:20 暂停）

用户在关 Wi-Fi、播视频（画面与进度条正常）的条件下复测，音频仍持续卡顿，**Wi-Fi/BT 射频共存已被排除**。此后做了三轮 3.2 Mbaud 尝试，全部未能提速率，但拿到了关键机理。

### 21.1 已证实的事实

1. **控制器在收下 NVM 的那一刻就切换速率**，不等 HCI_Reset。证据（`cmi-out/bt6_stop.log`）：
   ```
   TLV type=1 accepted: 188564 bytes     ← 补丁
   TLV type=2 accepted: 5733 bytes       ← NVM（tag17 byte1=0x11）
   HCI 0xc03 timed out RX=0 SIRQ=0       ← 下一条 Reset 在 115200 上再无回音
   ```
   这是"切晚了"的直接证据：主机还在 115200，控制器已经不在了。
2. **串行时钟的实证基准**：现网 115200 = 根 7.3728 MHz（384/15625）+ `GENI 0x48/0x4c = 0x41`，串行时钟 1.8432 MHz，倍率 16。
3. **204.8 MHz 根时钟不可用**：`root 256/375 cfg 0x41` 完全静默（`RX=0 SIRQ=0`），RCG 能锁但引擎不工作。
4. **`cfg 0x11`（分频 1）收到的是乱码**：大量 `unsolicited event=0xff`，说明分频字段语义与假设不符，速率不对。
5. 回退机制有效：`bt_link_restart` 重新上电 + 115200 重跑能把蓝牙救回来（用户实测"蓝牙正常打开并连接"）。

### 21.2 最后一版（`payload-bt1-3m2c.bin`，内核 `d2c6c357…`）的做法

不再用 NVM 盲试，改成可验证顺序：

- NVM 固定写 `0x00`（115200），链路完整跑通（Reset → 0x1001 → 0x1002 → 0x1009/BD_ADDR）；
- 然后 `0xfc48` 空操作（参数 0x00）探测厂商命令是否存在——不存在则原地停留，**不破坏任何东西**；
- 存在则 `0xfc48` 参数 `0x11`（3.2 Mbaud），控制器在旧速率应答后主机再切；
- 三个时钟候选保持同一串行时钟：`102.4 MHz+分频2`、`204.8+分频4`、`51.2+分频1`；
- 链接丢掉才 `EAGAIN` → 重新上电 + 115200 重跑。

**结果：用户实测仍卡顿**（蓝牙可用、能连、能出声）。`0xfc48` 是否被支持、三个候选里哪个命中，尚未读取日志确认。

### 21.3 复测时要看的三行（唯一判据）

`oem stop` 后 `fastboot get_staged` 拿前 1.5 MB，搜 `UMI BT`：

- `UMI BT: 0xfc48 no-op (115200) status=?` —— 非 0 表示芯片不认这条厂商命令，NVM 是唯一入口；
- `UMI BT: link at 3.2 Mbaud: root … cfg …` —— 成功；
- `UMI BT: no reply at 3.2 Mbaud with root …` —— 该候选没命中。

注意：`UMI BT:` 这些行**不在内核实时环形缓冲里**（`oem log` 抓不到），只有 `oem stop` 全量导出才有；`logdump` 分区这条路可能是空的，`get_staged` 才可靠。

### 21.4 下一步的可能方向（未做）

1. **读一次 21.3 的三行**，先确定 `0xfc48` 存不存在——这决定后续是调时钟还是换机制。
2. 若 `0xfc48` 可用但时钟不中：做**速率扫描**（参考 `instantnoodle_bt.c` 的 `bt=3` 做法），把 `(m,n,div)` 候选按串行时钟从 25.6/51.2/102.4 MHz 铺开，逐个发 `0x1001`，谁应答就是谁；每次前先 `bt_rx_drain()` 清 FIFO 与 H4 状态。
3. 若 `0xfc48` 不可用：只能回到 NVM 路径，但**切换点必须在 NVM 确认之后立刻切主机**（本轮已验证），并且必须能容忍失败——即先 `0xfc48` 之类的方式确认，否则一次错误就要重新上电。
4. 另有一条与带宽无关的怀疑：`bt_control_worker` 的 1 ms 轮询与 QCA in-band sleep（0xfd/0xfc）握手在高码率下可能跟不上，参考实现注释明确写过"1 ms 轮询撑不住 3.2 Mbaud"。若速率确认无误仍卡，应把 worker 间隔降到 200 µs 并检查 IBS 应答时序。

### 21.5 当前设备状态（可继续使用）

系统镜像 `system-zh7-btaudio.apfs`（蓝牙音频可用）、ramdisk 与 cmdline 为 bt1 原件、内核为本轮 `d2c6c357…`。蓝牙可连可出声但卡顿；触摸、显示、Wi‑Fi 正常。**无回滚必要。**

### 22.6 音频被弄哑（2026-11-19 11:45–11:55）

**现象**：震动驱动一启用（连 `umi_haptic=1` 只读探测也）就完全没声音；回滚到不含该驱动的 `payload-bt1-3m2c.bin` 才有声音。

**设备树核查**（`cmi-stock/boot_stock.dtb`，工具 `tools/fdt_find.py`）：

| 事实 | 值 |
|---|---|
| 引脚控制器 | `/soc/pinctrl@f000000`，`compatible = qcom,kona-pinctrl`，`reg = 0xf000000 0x1000000`（**16 MB**，即 gpio n 在 base + 0x1000·n，n 可达 4096） |
| 震动复位 | `aw8697_gpio_reset` → gpio130，`output-low` |
| 震动中断 | `aw8697_gpio_int` → gpio129，`bias-pull-up` |
| gpio130 复用 | 同时被 `cam_sensor_active_4` / `cam_sensor_active_6dofleft` 使用（不同机型变体） |
| gpio60/61 | **整棵引脚表里没有**任何 pin group 使用它们 |
| 各 i2c 总线 | boot dtb 里除 `i2c@884000`（fsa4480/nq）外全部 `disabled`，真实配置在 dtbo 里，本仓库没有 |

**由此得到的两个疑点：**

1. **基址不一致**：现有驱动用 `0x0f100000`，震动 UMI 路径用 `0x0f500000`，而设备树写的是 `0x0f000000`（16 MB 窗口）。`0x0f500000 + 0x1000·60` 与 `0x0f000000 + 0x1000·60` 相差 0x500000，两者不可能同时正确。但震动确实通过 `0x0f500000` 读到了 AW8697 的 ID（0x97），说明那一对引脚在 `0x0f500000` 窗口下是可用的——也就是说这台机器可能存在**两个 TLMM 视图**，或者 boot dtb 的 reg 与内核实际映射不一致。
2. **引脚归属未知**：60/61 不在设备树任何 pin group 里，无法确认它们除震动外还属于谁。

**当前结论**：问题出在**引脚层面**（复位脚 130 或 I2C 的 60/61），不是马达驱动、波形或升压。下一步用 boot-arg 关掉复位脚单独复测来二分。

**验证顺序**：先确认 `payload-bt1-3m2c.bin` 下声音正常（这一步同时能排除"音频是被 3.2 Mbaud 那轮内核改动弄坏的"）。

### 22.7 定论：引脚没配错，但驱动会把音频留在关断态（11:55–12:05）

从 Android 侧读到的**权威事实**（`su` 读取 `/proc/device-tree` 与 `/sys/bus/i2c/devices`）：

| 项 | 值 |
|---|---|
| 震动挂载 | `aw8697_haptic 2-005a` → `/soc/i2c@a8c000`，**i2c-2**，该总线只有它一个设备 |
| 该总线引脚 | `qupv3_se11_i2c_active` = **gpio60 / gpio61**（function qup11）→ 与驱动假设一致 |
| 震动复位/中断 | `reset-gpio = <0x65 0x82>` = **gpio130**；`irq-gpio = <0x65 0x81>` = **gpio129** → 与驱动一致 |
| 功放 | **CS35L41**（不是 AW88261），在 `i2c@98c000` = i2c-1，0x40/0x42 |
| 冲突 | 无。功放用 i2c-1，震动用 i2c-2，引脚不重叠 |

**所以引脚编号全部正确，驱动没有配错脚。** 但现象是：只要震动驱动跑过（哪怕只读 level 1），iOS 就完全没声音；而且**软重启也不恢复**——回滚到不含该驱动的同一内核仍然哑。**进一次 Android 再回 iOS，音频就恢复**（`umi-audio: amp 0x40: protection firmware … verified in DSP memory`）。

结论：震动驱动把 CS35L41 留在了一个 "speaker disabled" 的锁存状态，而 iOS 侧重启不会重新初始化功放，只有 Android 的驱动会。复现代价因此很高：**每次试震动后都必须进一次 Android 才能把声音换回来**。

**待查（下一步）**：设备树的引脚控制器是 `qcom,kona-pinctrl @ 0x0f000000`（16 MB 窗口），而驱动用 `0x0f500000` 算偏移，二者差 0x500000。需要加一个**只读**诊断，把两个窗口下 gpio130/60/61 的寄存器值并排打印出来，看哪个窗口的值符合设备树描述的初始状态（input / pull-down / drive 2 mA），从而确定真实基址。在此之前不要再用震动驱动开机。

**当前状态**：设备运行 `payload-bt1-3m2c.bin`（无震动驱动），音频恢复正常，蓝牙可用但 A2DP 仍卡顿。

### 23.2 为什么是 API 导入而不是 git push

本机 `git` 的 HTTPS 通道不可用：

| 路径 | 结果 |
|---|---|
| 经代理 `127.0.0.1:52420` | `CONNECT github.com:443` → **502 Bad Gateway**（代理只放通 `api.github.com`） |
| 绕过代理直连 `github.com` | `Could not connect to server`（DNS 解析到 20.247.166.64，不可达） |
| 直连 `api.github.com` | ✅ 稳定，约 0.45 秒/次 |

因此用 `tools/gh_import.py` 走 Git Data API：blobs → tree → commit → ref。

### 23.3 途中踩的四个坑（下次直接用）

1. **空仓库不能调 blob API** → `409 Git Repository is empty`。先 PUT 一个 `README.md` 建首个提交。
2. **次级限流** → 8 线程并发出 300 个 blob 后被 403 `secondary rate limit`。改为顺序 + 约 1 次/秒 + 75 秒退避。
3. **代理间歇 502** → 脚本原本只对 HTTPError 重试，`URLError` 直接崩；补上网络错误重试。
4. **`refs/heads/main` 已存在** → POST 建 ref 报 `422 Reference already exists`，改用 `PATCH .../git/refs/heads/main {sha, force:true}`。
5. 缓存文件路径不能用 `/tmp`（Windows 版 Python 不认），改 `tempfile.gettempdir()`；缓存让任务可断点续传。

### 23.4 权限相关

- fine-grained token **不能创建仓库，也不能 fork**（403 `Resource not accessible by personal access token`），必须在网页建空仓库。
- token 必须把 **Contents 设为 Read and write**；只读 token 连 blob 都建不了（403）。
- `xm6661885/hakios-xnu-kernel-umi-fixes` 对 `<redacted>52013140-droid` 是 `push: false`，直接推不可能；要向原仓库贡献只能 fork + PR。
